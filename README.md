# rolling-memory — 两层滚动记忆

解决对话客户端只有有限消息窗口（比如只保留最近 19 句）导致的"失忆"：
滑出窗口的消息被异步结算成摘要，每次请求自动注入回上下文，LLM 永远知道"之前聊过什么"。

本项目提取自一个私人 AI 伴侣项目的记忆系统，去掉了全部业务耦合，只保留通用的记忆层。

> ⚠️ **先读这段：本模块是"防失忆"，不是记忆库，也不能代替记忆库。**
>
> 很多人第一眼会把它当成"AI 的记忆系统"，然后用它去承担本该由检索式记忆库承担的工作，结果发现"远期的事怎么问不到了"。这是设计使然，不是 bug。
>
> | | 滚动记忆（本项目） | 外置记忆库 |
> |---|---|---|
> | 存取方式 | 摘要，**全量注入**每轮上下文 | 检索，按需**召回相关片段** |
> | 覆盖范围 | 近两天左右（T1）+ 更早的骨架（T2） | 不受时间限制，写进去就一直能查 |
> | 精度 | 有损压缩，细节会丢 | 原文/结构化，可精确复现 |
> | 解决的问题 | 客户端窗口太小，**紧接着的对话**接不上 | 长期事实、偏好、事件需要随时调取 |
>
> 两者是互补关系：**紧接着的衔接**交给滚动记忆，**深挖历史**交给记忆库。
>
> 特别说明 **T2 的定位是"噪声沉降池"**：它刻意把远期话题压缩成极短的骨架，让不再需要的旧细节自然滑出。所以"T2 里的东西查不到了"是预期行为——需要长期保留的内容应该一开始就写进记忆库，而不是指望 T2 帮你留着。

## 这个模块部署在哪？谁都能用吗？

rolling-memory **不是一个独立服务，而是嵌在"中间层"里的模块**——它需要一个位置，能同时看到"客户端发来的消息数组"（观察滑窗）和"即将发给 LLM 的最终消息数组"（注入摘要）。三种情况：

| 你的现状 | 接法 | 难度 |
|---|---|---|
| **有自己的网关/中转**（自建 API 代理、转发服务） | 三件套接入（见下文） | 5 分钟，加 3 行代码 |
| **没有网关，客户端只能填 API 地址**（大多数 App 用户） | 用内置的本地转发代理 `npm run proxy` | 装好 Node 后改一个网址，无需写代码 |
| **客户端直连 LLM 且中间什么都装不了** | 用不了——本模块必须有个位置拦截/注入请求 | — |

## 架构

```
窗口原文 N 条     客户端原样（改不了，也不需要改）
   ↓ 每句滑出（指纹检测自动发现），攒够一批结算一次
结算只产出三样：append 新话题行 / close 已结束旧行 / state 状态节
   ↓
T1 近期摘要       有序话题行列表 + 状态节，≤1500 字
   ↓ 超限 → 从最旧端机械摘行（摘到 ≤ 上限），交给一次小调用
T2 远期梗概       有序梗概行列表，≤360 字（噪声沉降池，刻意丢弃细节）
                 按 7 天 + 字数双淘汰，最旧的直接丢
```

**这是真滚动，不是"整段重写 + 攒满清零"**（v1.3 改动）：

| | 旧实现 | 现在 |
|---|---|---|
| 结算输出 | 重写整段 T1（上千字） | 只输出新增行 + close 列表（几百字） |
| T1 超限 | 整段压成 T2 后 **清空 T1**（近 24h 细节瞬间塌掉） | 从最旧端**摘几行**，其余原样留着 |
| T2 更新 | 只在 T1 压缩时被重写 | 摘出的行并入（输入只有那几行 + 现有 T2） |
| T2 淘汰 | **无**（很旧的梗概能一直挂着） | 7 天日期淘汰 + 字数淘汰 |
| 待办 | 只写不核，完成的也一直挂着 | 模型必须把**已结束**的旧行填进 `close` 销项 |

## 核心设计

1. **滑窗指纹重叠检测**：客户端每次请求都带完整窗口历史，模块对消息做指纹
   （`sha256(role+"\0"+text)` 取前 16 位）比对——本轮请求的**前缀**恰好是上一轮的**后缀**，
   重叠段之外的前段就是"刚滑出窗口"的消息。天然免疫三类干扰：
   - 客户端重发/重试同一批消息（指纹去重，不重复结算）
   - 会话切换/新开窗口（整窗旧消息一次性兜底结算，不丢尾巴）
   - 标题生成等后台小请求（**本轮消息数极少且与上轮零重合**→ 判为后台请求，
     不当换窗处理。判据必须是"本轮少"，不是"上轮少"——后者实战里永远不成立）
2. **结算前强制重读盘**：每次结算前先从磁盘重读 `summaries.json` 再合并。
   外部脚本/人工直接改摘要文件，不会被内存里的旧状态覆盖。
3. **待办销项（close）**：结算时模型必须标出**已明确结束**的旧话题行（待办做完了、
   约定履行了、话题有结论了），代码按时间戳前缀把这些行删掉——完成的待办不再一直挂着。
4. **机械淘汰，不靠模型控长度**：T1 超限时由代码从**最旧端**摘行（摘到 ≤ 上限，
   保底留 `minKeepT1` 行），交给一次小调用并入 T2。长度控制是确定性的，模型只管写足。
5. **T2 双淘汰**：先按**日期**丢过期行（默认 7 天），再按**字数**丢最旧行。
   最旧的梗概不再永久保留。
6. **异步结算，永不阻塞**：结算在后台跑，失败自动把消息放回缓冲重试；
   缓冲超上限丢最旧，防内存膨胀。解析失败会先原地重试一次，仍失败才归档。
7. **静默降级**：配置缺失、接口挂了、文件损坏——只打日志，主对话链路照常。
8. **零依赖**：原生 Node（≥18，内置 `fetch`），单文件接入。
9. **可观测**：每次结算调用都会输出一行 `llm_usage` 日志（含 prompt_tokens /
   cache_hit / cache_miss / completion_tokens）。没有这行日志，"结算花了多少钱、
   有没有命中缓存"就只能靠猜。

## 接入（三件套）

```js
const rolling = require("rolling-memory");
rolling.init(); // 网关启动时调用一次，读环境变量

// 网关每次收到请求、转发给 LLM 之前：
rolling.observeRequest(messages);

// 组装发给 LLM 的消息时，把摘要块追加在末尾（注意力最高位）：
for (const blk of rolling.injectBlocks()) messages.push(blk);
```

就这些。其他一切（攒批、去重、结算、压缩、落盘、重试）都在模块内部完成。

## 没有网关？用内置的本地转发代理

大多数聊天 App 的设置里只有一栏「API 地址」。这时不需要写任何代码：

1. 安装 Node.js（≥18），下载本仓库，复制 `.env.example` 为 `.env` 并填好三个必配项
2. 在仓库目录运行：

```bash
npm run proxy
```

3. 把客户端里的 API 地址改成 `http://127.0.0.1:8787/v1/chat/completions`——**密钥原样不动，模型名原样不动**

之后客户端的每次请求都会经过代理：滑出的消息被自动结算成摘要，下轮请求自动带上。响应（含流式输出）原样透传，客户端无感知。端口可在 `.env` 里用 `PROXY_PORT` 改。

## 双上游：对话用 A 家，结算用 B 家

这是被问得最多的配置问题，先说结论：**支持，而且这是推荐用法。**

### 为什么需要分开

滚动记忆每轮要做两件性质完全不同的事：

| | 对话链路 | 结算链路 |
|---|---|---|
| 干什么 | 真正跟你聊天 | 把滑出的消息压成摘要 |
| 对模型的要求 | 要聪明、要有文风 | 只要会归纳，越便宜越好 |
| 频率 | 每轮都跑 | 攒够一批才跑一次 |
| 能否命中前缀缓存 | **能**（窗口前缀基本不变） | **几乎不能**（见下） |

**关键差异在缓存。** 前缀缓存靠"字节完全相同的前缀"命中。对话链路的 messages 是逐轮增长的，前缀稳定，命中率很高。但结算链路的 prompt 长这样：

```
[当前摘要] ← 每轮都在变
[新对话]   ← 每轮都在变
```

输入的主体**每轮都是全新的**，所以结算这条链路必然接近 0% 缓存命中、全价计费。这是任务性质决定的，不是实现缺陷——**没有"让结算命中缓存"的办法**，除非你放弃增量结算。

既然结算注定全价，那策略就明确了：**让结算走最便宜的模型，把省下的钱花在对话模型上。** 硬把两者绑在同一个上游，等于逼你二选一：要么对话用便宜模型（体验差），要么结算用贵模型（白烧钱）。

### 怎么配

```bash
# 结算上游 —— 便宜的快模型
LEDGER_API_URL=https://api.deepseek.com/v1/chat/completions
LEDGER_API_KEY=sk-deepseek-xxx
LEDGER_MODEL=deepseek-chat

# 对话上游 —— 你要的那个好模型
CHAT_API_URL=https://api.x.ai/v1/chat/completions
CHAT_API_KEY=xai-xxx
```

- 用**内置代理**（`npm run proxy`）时：对话走 `CHAT_API_URL`，结算走 `LEDGER_API_URL`，两者独立。
- 用**自己的网关**（三件套接入）时：本模块只负责结算一侧，永远读 `LEDGER_*`；
  对话上游由你的网关自己管——等于天然就是双上游。

### 密钥优先级（用代理时）

```
客户端请求自带的 Authorization  >  CHAT_API_KEY  >  LEDGER_API_KEY
```

也就是说：**你通常什么都不用做。** 大多数客户端只要把 API 地址改成代理地址就行，密钥原样保留、原样透传。只有当客户端不带密钥（或你想统一托管密钥）时，才需要填 `CHAT_API_KEY`。

### 不填 CHAT_API_URL 会怎样

回退到 `LEDGER_API_URL`，即对话与结算同源——也就是旧版本的行为。**向后兼容，老配置不用改。**

### ⚠️ 一个常见误解：多开 Key 不能提升并发

有些厂商（如 DeepSeek）的并发/限流是按**账号**算的，同一个账号下开 10 个 Key 也还是那一个额度。**双上游解决的是"模型选择自由"和"计费口径解耦"，不是限流问题。** 如果你的目标是绕开配额，双上游帮不了你，得换账号或换厂商。

## 迷你查看器

另开一个终端运行：

```bash
npm run view
```

浏览器打开 http://127.0.0.1:8788 ，只读展示 T1/T2 当前内容、字数余量、待结算缓冲，每 5 秒自动刷新。想人工修正记忆，直接编辑 `state/summaries.json`，模块下次结算前会重读它。

## 配置

复制 `.env.example` 为 `.env`（或直接设环境变量）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `LEDGER_API_URL` | （必配） | **结算**上游，OpenAI 兼容 chat/completions 地址 |
| `LEDGER_API_KEY` | （必配） | 结算接口密钥 |
| `LEDGER_MODEL` | （必配） | 结算用模型（建议便宜的快模型） |
| `CHAT_API_URL` | 空 | **对话**上游（仅 `npm run proxy` 用）。不填则回退 `LEDGER_API_URL` |
| `CHAT_API_KEY` | 空 | 对话上游密钥。客户端自带 Authorization 时可不填 |
| `LEDGER_BUFFER_COUNT` | 6 | 攒够多少**条**触发一次结算（主判据） |
| `LEDGER_BUFFER_CHARS` | 400 | 攒够多少**字**触发一次结算（超长兜底） |
| `LEDGER_T1_MAX_CHARS` | 1500 | T1（话题行 + 状态节）超过则从最旧端摘行并入 T2 |
| `LEDGER_T2_MAX_CHARS` | 360 | T2 封顶（v1.3：220→360） |
| `LEDGER_T2_MAX_DAYS` | 7 | T2 日期淘汰：比这更旧的行直接丢 |
| `LEDGER_MIN_KEEP_T1` | 3 | T1 淘汰保底行数（防一次结算把 T1 摘空） |
| `LEDGER_PENDING_MAX_CHARS` | 12000 | 待结算缓冲上限（防结算连续失败时膨胀） |
| `LEDGER_USER_LABEL` | user | 摘要里"对方"的称呼 |
| `LEDGER_ASSISTANT_LABEL` | assistant | 摘要里"自己"的称呼 |
| `LEDGER_LLM_TIMEOUT_MS` | 60000 | 结算接口超时 |
| `LEDGER_ENABLED` | true | 总开关 |
| `ROLLING_MEMORY_STATE_DIR` | 模块内 `state/` | 摘要落盘目录（可选） |
| `PROXY_PORT` | 8787 | 本地转发代理端口（`npm run proxy`） |
| `VIEWER_PORT` | 8788 | 迷你查看器端口（`npm run view`） |

兼容别名：`TARGET_API_URL` / `TARGET_API_KEY` 等效于 `LEDGER_API_URL` / `LEDGER_API_KEY`。

### 关于 `LEDGER_T1_MAX_CHARS`：长度由代码控制，模型只管写足

**1500 是「话题行 + 状态节」的总和上限。** 超了不会整段重写或清空——代码从**最旧端**机械摘行，
把摘出的行并入 T2，剩下的原样留着。所以模型可以放心把每条话题写足（40~90 字），
不必为了"塞下更多话题"把每条压成几个字：长度是确定性的，不是模型自己权衡出来的。

想调大调小都可以，效果是可预期的：调大 = T1 覆盖更长的近期窗口（注入更贵）；
调小 = 更早的话题更快滚进 T2。`LEDGER_MIN_KEEP_T1` 是保底——一次结算至少留这么多行，
防止极端情况下把 T1 摘空。

## 摘要格式

T1 固定两节，结算 prompt 已内置。结算只输出三个字段（**不再重写整段 T1**）：

```
append：本批新话题行。每条一行，开头带【绝对时间戳】（如 9.23日 09:10），行内不换行；
        关键动作/原话/数字量词写足，每条 40~90 字；约定/待办/没聊完的话头也写成话题行。
        没有新内容就输出空数组；不要重复[近期摘要]里已经写过的事。
close ：[近期摘要]里【已经明确结束】的旧行起始时间戳（待办做完了/约定履行了/话题有结论了）。
        没结束的不填，拿不准不填。待办一旦完成必须 close 掉，不许一直挂着。
state ：第 2 节「<userLabel>的状态和心情」整体重写，只留最新（体力/情绪/在忙什么），
        开头带检查时刻的时间戳。
```

T1 渲染成两节（第 1 节最新在前，与原样式一致）：

```
一、聊了什么
9.23日 09:10：……
二、<userLabel>的状态和心情
9.23日 09:15：……
```

**为什么强制绝对时间戳**：早期 prompt 要求写"今天上午 / 刚才 / 昨晚"，但这类相对词过几天读起来会误导成"最近发生"（"今天"在每天滚动中语义会漂移）。现在要求写绝对时间，并由模块注入 `[当前时间]` 锚点供 LLM 换算。

T2 压缩规则（摘行并入时的一次小调用）：每条必须**能独立读懂**（写清是谁、什么事、什么结论，禁电报体、禁悬空指代）；绝对时间戳必须保留（较久远的可简化到 `M.D日`，但严禁改成相对词）；闲聊细节全删，只留事实骨架与情绪转折。T2 按 7 天 + 字数双淘汰。

## 数据

所有状态落在 `state/summaries.json`。v1.3 起是**结构化行列表 + 字符串镜像**：

```jsonc
{
  "t1_lines": [{ "ts": "9.22日 19:45—20:10", "text": "9.22日 19:45—20:10：…" }], // 升序，最旧在前
  "t1_state": "9.22日 20:10：体力——…",                                          // 状态节，每次整体重写
  "t2_lines": [{ "ts": "9.21 16:45", "text": "…" }],                             // 升序
  "t1": "…",  // 字符串镜像（renderT1 产物），供 viewer.js / stats() 直接读
  "t2": "…",  // 字符串镜像（renderT2 产物），格式与旧版一致
  "updated_at": "2026-09-22T12:10:46.837Z"
}
```

> **旧的 `{t1,t2}` 纯字符串格式会在启动时自动迁移**：按行拆开（行内换行并回上一条）、
> 切出状态节、T2 按日期切段，**不压缩、不清空，内容全保留**。

想改口径、想人工修正记忆，直接改这个文件即可——模块下次结算前会重读它。
（手改后建议重启进程：`loadSummary()` 只在 `init()` 与 `settleBatch()` 时重读磁盘。）

另有两个**只增不改的归档目录**，用于兜底排查：

| 目录 | 什么时候写 | 为什么留着 |
|---|---|---|
| `state/t1_archive/` | T1 超限、摘行并入 T2 前 | 摘走的细节只活在归档里（T2 只剩骨架），归档留一份原文供人工捞回 |
| `state/failed_batches/` | 结算返回内容无法解析、且重试一次仍失败时 | 这批消息在这一轮里等于消失了。落盘保留原始返回 + 消息内容，便于事后归因（是模型不听话还是 prompt 有问题） |


## 常见问题

**Q：能对话用 Grok、总结用 DeepSeek 吗？**
能，这是推荐配置。见上文「双上游」。用代理时填 `CHAT_API_URL` + `LEDGER_API_URL`；用自己的网关时天生就是分开的。

**Q：为什么结算的缓存命中率几乎是 0？能不能优化？**
不能——**这是任务性质决定的**。结算的输入主体（`[当前摘要]` + `[新对话]`）每轮都是全新的，前缀缓存靠"字节完全相同的前缀"命中，所以必然 miss、必然全价。唯一能做的是把**固定指令挪进 system prompt**（本模块已做），让固定部分稳定命中，但这也只能覆盖很小一段。结论：**接受结算全价，然后让结算走最便宜的模型。**

**Q：多开几个 Key 能提升并发吗？**
一般不能。多数字段的并发/限流按**账号**计（如 DeepSeek），同账号下多个 Key 共享同一额度。双上游不是用来绕限流的。

**Q：T2 里更早的事为什么查不到了？**
这是设计意图。T2 是"噪声沉降池"，刻意压缩远期话题、丢弃细节，让不再需要的旧信息自然滑出。需要长期保留的内容请写进专门的外置记忆库，不要指望 T2。

**Q：摘要每条都好短，信息全丢了？**
先检查 `LEDGER_T1_MAX_CHARS`。v1.3 起长度由代码机械控制（超限摘最旧的行进 T2），
所以正常不会出现"为了塞话题数把每条压成几个字"的情况——如果摘要仍然很短，
多半是结算模型太弱或不听话，换一个归纳能力更好的模型试试。另外别忘了本模块只覆盖近期，
更早的信息本来就会滚进 T2 并最终被淘汰。

**Q：客户端窗口很大（几百条），还需要它吗？**
窗口越大，需要滚动记忆的场景越少。但如果窗口是**按条数**截断的，而你的对话单条很长，依然会滑出——此时它仍是必要的。
