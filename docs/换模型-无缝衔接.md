# 换对话模型，记忆怎么不断

> 这篇回答一个被问得最多的问题：
>
> **「我能不能用 DeepSeek 做总结、对话随时换成 Gemini / GPT / Grok，但记忆还是连着的？」**
>
> 能。而且这是本项目的推荐用法，不是勉强支持。但有几条边界必须先讲清楚——**哪些能无缝、哪些一定会断、断了怎么救**，都在下面。

---

## 一、三句话结论

1. **记忆存在一个 JSON 文件里，跟模型完全无关。** 换对话模型，记忆文件一个字节都不会变。
2. **总结模型和对话模型本来就是分开的两条链路**（v1.2 起支持双上游），换对话模型碰不到总结那条。
3. **唯一会让记忆断掉的动作不是「换模型」，是「换模型时新开了一个对话」。** 这两件事在客户端里常常挤在同一个按钮上，所以被混为一谈。

---

## 二、为什么能无缝（原理，三行）

```
① 记忆的存储   →  state/summaries.json（默认会话）或 state/sessions/<id>.json
                  纯本地 JSON，没有任何模型厂商相关的字段

② 滑窗的识别   →  指纹 = sha256(role + "\0" + 文本)，只依赖「谁说的、说了什么」
                  **不看模型名、不看 session id、不看时间戳**

③ 记忆的注入   →  每轮请求末尾追加一段 system 消息（滚动摘要）
                  谁在读这段摘要，谁就"记得"；写它的可以是另一个模型
```

所以这件事在机制上是成立的：**A 模型写的摘要，B 模型照样读得懂**——因为摘要就是普通中文，不是某种模型的私有格式。

反过来，同一件事也解释了它的边界：摘要里**没有"这个模型说话是什么风格"这种信息**，所以换模型后人格和气场会变（见限制 3）。

---

## 三、怎么配（中转站用户照抄）

### 3.1 两条链路分开

```bash
# 结算链路 —— 固定一家，越便宜越好
LEDGER_API_URL=https://api.deepseek.com/v1/chat/completions
LEDGER_API_KEY=sk-你的deepseek-key
LEDGER_MODEL=deepseek-chat

# 对话链路 —— 走你的中转站（客户端自带的密钥会原样透传，这条甚至可以不填密码）
CHAT_API_URL=https://你的中转站/v1/chat/completions
# CHAT_API_KEY 留空即可
```

### 3.2 客户端只改一栏

聊天 App 里把「接口地址」改成代理地址：

```
http://127.0.0.1:8787/v1/chat/completions
```

**密钥不用动，模型名不用动。** 之后你想在客户端里把模型从 `deepseek-chat` 切成 `gemini-2.5-pro`、再切成 `gpt-4o`，代理一个字都不拦——它会原样把 `model` 字段转发给你的中转站（这一点有实测，见第五节）。

### 3.3 为什么结算要走便宜的

结算链路的 prompt 长这样：

```
[当前摘要] ← 每轮都变
[新对话]   ← 每轮都变
```

输入主体**每轮都是全新的**，前缀缓存必然 miss、必然全价。这是任务性质决定的，没有优化空间。既然注定全价，就让它走最便宜的模型，把预算留给对话。

## 四、会不会断：五种场景逐条说

| 你的操作 | 会不会断 | 实际发生什么 |
|---|---|---|
| **在同一个会话里**把模型从 A 换成 B | ✅ **完全不断** | 客户端照样把历史发过来，摘要照常注入。B 一上来就知道之前聊过什么 |
| 换完模型后**继续用原来的对话** | ✅ 不断 | 同上，这是最常见也最推荐的做法 |
| 换模型时**新开了一个对话** | ⚠️ **会分家** | 新对话是新的记忆档，从零开始。**旧的那份不会丢**，切回去还在 |
| **两个会话同时用**（一个聊感情一个写代码） | ✅ v1.9 起各自独立 | 以前会串成一条时间线，现在各记各的 |
| 换模型 + 新开对话 + 还想接着聊 | ⚠️ 需要手动搬 | 见限制 2 的三种解法 |

> **一句话记住**：**换模型是换"谁来回答"，不是换"跟谁在聊"。** 只要客户端眼里还是同一个对话，记忆就一直在。

## 五、实测数据（v1.8 → v1.9 到底修了什么）

这一节是本文最有用的部分：**下面每个数字都是跑出来的，不是推的。**

复现命令：`npm run bench:sessions`（脚本在 `_bench_sessions.js`）

同样一份输入：**两个会话各聊 8 轮、交替发送、客户端窗口只留 4 条**。

| 指标 | v1.8（一份摘要） | v1.9（会话隔离） |
|---|---|---|
| 送去结算的消息条数 | **39** | **8** |
| 其中重复的消息 | **24** | **0** |
| 识别出的会话数 | 1 | 2 |
| 串味的会话（同时含两边内容） | **1（全串了）** | **0** |
| T1 最终行数 | 39（大半是重复） | 8（各 4 行） |

v1.8 的病因不是"换窗逻辑写错了"，是**只有一份摘要**：A 说一句、B 说一句，两边的窗口轮流被当成"滑出"倒进同一份摘要，于是同一条消息被记了 2~4 次，两个不相干的话题串成一条时间线。

v1.9 的做法是**先认领会话，再走滑窗**——认领这一步见下一节。

另外两条实测（这两条和版本无关，是机制决定的）：

- **同一会话内换模型**：连续 8 轮、前 4 轮 DeepSeek 后 4 轮 Gemini → 摘要 0 重复、内容连续。
- **代理对 `model` 字段**：`deepseek-chat` / `gemini-2.5-pro` / `gpt-4o` 三个名字原样到达上游，一字不改。

## 六、限制（重点，请逐条看）

### 限制 1：切模型时**别新开对话**

这是唯一真正会让记忆"看起来断了"的操作。

**为什么**：客户端新开对话 = 请求里的历史被清空 = 与上一轮零重合。记忆层看到的是"一个全新的窗口"，它只能当新会话处理。

**v1.9 的行为（已修好的一面）**：
- 新对话会开一份**独立的**记忆，不会污染旧的那份（v1.8 会把旧窗口整个吞进当前摘要——这才是真污染）。
- 旧记忆原样留在磁盘上，切回去还在。

**做不到的一面**：
- 新对话**不会自动继承**旧对话的记忆。没有任何机制能猜到"这两个对话是同一个人接着聊的"。

**想接着聊怎么办**：
1. **最好的办法：别新开。** 在客户端里换模型通常不需要新开会话（NextChat / ChatBox / LobeChat 都是同一个对话里换模型）。
2. 如果客户端强制新开：让新对话第一句话带上上下文（"接着刚才聊的，我们在说 X"），摘要会在几轮后自己长出来。
3. 手动搬：用 `npm run view` 打开查看器，把旧会话的 T1 内容复制到新会话里（查看器可以就地编辑）。

---

### 限制 2：会话识别是**启发式**的，不是 100%

v1.9 靠三条线索认领会话，可靠性从高到低：

| 线索 | 可靠性 | 什么时候有 |
|---|---|---|
| 调用方显式给的 id | **100%** | 请求头 `x-rolling-session` 或 body 里的 `session_id` |
| 窗口重叠（本轮前缀 == 上轮后缀） | 高 | 同一会话里客户端一定会带历史，所以几乎总有 |
| 冷启动归一化（归给最近写过的会话） | 中 | 进程刚启动的第一个请求 |

**认不出来的情况**（会退化成"开一个新会话"）：

- 客户端窗口整体滑走（一次发了好几条、旧消息全部出窗）→ 判成新会话，**记忆不丢，只是分家**
- 客户端每轮只发最后一条消息（不带历史）→ 每个请求都会被当成新会话，**这种情况本模块本来也用不了**（它依赖窗口重叠）
- 多人共用一个代理 → 建议每人一个显式 id

**怎么做到 100% 准**：

```bash
# 客户端能配自定义请求头的话（很多自建客户端可以）
x-rolling-session: phone-living
```

或者请求体里带：

```json
{ "model": "...", "messages": [...], "session_id": "phone-living" }
```

内置代理会读这两个地方，读到就直接用，不再猜。

---

### 限制 3：人格连续性**不归滚动记忆管**

这条最容易被误解，单独说清楚：

| | 谁负责 |
|---|---|
| 记得"我们昨天聊了什么" | **滚动记忆** ✅ |
| 说话像不像同一个人、语气对不对 | **system prompt（人设卡）** ❌ 不是滚动记忆 |

换到 Gemini 之后，如果客户端把 system prompt 一起带过去了，人格基本连贯；如果客户端切模型时把 system prompt 换了/丢了，那就会"换了个魂"——**这跟滚动记忆一点关系都没有**，滚动记忆只是把"聊过什么"告诉新模型。

所以判断"换模型后像不像原来那个人"，先看 system prompt 有没有跟着走。

---

### 限制 4：摘要是有损的，换模型看到的不是原文

滚动记忆给到新模型的是**摘要**（T1 ≤1500 字 / T2 ≤360 字），只有窗口里那十几条是原文。

所以换模型后可能出现：
- 细节接不上（"你上次说的那个词是什么"——摘要里没这个词）
- 语气断层（摘要记录的是事实，不记录语气）

**想更细**：调大 `LEDGER_T1_MAX_CHARS`（代价是每轮注入更贵），或者用外置记忆库做检索式召回。

---

### 限制 5：T2 是**故意**丢细节的

T2（远期梗概）的设计定位是"噪声沉降池"：7 天 + 360 字双淘汰，越旧越简，最后直接丢。

所以"T2 里更早的事查不到了"**不是 bug**。需要长期保留的事实请写进专门的外置记忆库，别指望 T2。

---

### 限制 6：中转站要能接受结算用的三个字段

结算请求会带：

```json
{ "response_format": { "type": "json_object" }, "reasoning_effort": "minimal", "max_tokens": 4000 }
```

**没有降级路径**：非 2xx 直接抛错 → 消息退回缓冲 → 下轮重试 → 一直失败的话，缓冲涨到 `LEDGER_PENDING_MAX_CHARS`（默认 12000 字）就开始**丢最旧的**。

所以用中转站时**先单独验一次结算**（聊几句，看有没有 `llm_usage` 日志）。不认这些字段的中转站，会让结算静默失败。

> 用官方直连（如 api.deepseek.com）最稳。

---

### 限制 7：多开 Key 不能提升并发

多数字段（含 DeepSeek）的并发/限流按**账号**算，同账号下开 10 个 Key 还是那一个额度。双上游解决的是"模型选择自由"和"计费口径解耦"，**不是限流**。

## 七、排查表

| 症状 | 可能原因 | 怎么办 |
|---|---|---|
| 换模型后完全不记得之前聊的 | 客户端新开了对话 | 看限制 1；切回原对话试试 |
| 记忆里混进了另一个会话的内容 | 没开隔离（v1.8），或没给 session id | 升到 v1.9；或给客户端配 `x-rolling-session` |
| 换模型后说话风格完全变了 | system prompt 没跟着走 | 看限制 3，不是记忆的问题 |
| 摘要更新了但内容很简略 | T2 在淘汰，或 T1 上限太小 | 调 `LEDGER_T1_MAX_CHARS`；长期事实写记忆库 |
| 完全没有 `llm_usage` 日志 | 结算根本没跑（阈值没到或配置错） | 检查 `LEDGER_*` 三项；把 `LEDGER_BUFFER_COUNT` 调小试试 |
| 有日志但摘要不变 | 中转站不认 `response_format`，返回内容解析失败 | 看 `state/failed_batches/`；换官方直连 |
| 会话越开越多 | 客户端窗口整体滑走，被拆成新会话 | 给客户端配显式 session id（限制 2） |

---

## 八、一句话总结

**换模型不会断记忆，换对话才会。** 因为它记的是"聊过什么"（存在本地文件里），不是"谁在聊"（那是 system prompt 的事）。

v1.9 起，多个会话也不会再互相污染——但如果你能顺手给客户端配一个会话标识，那就从"基本准"变成"一定准"。
